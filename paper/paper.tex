\title{Benchmarking JavaScript Bundlers at Scale:\\A Two-Tier Empirical Study of Vite, Rspack, esbuild, Webpack, and Rollup}

\author[addr1]{[Author Name]}
\address[addr1]{[Affiliation]}

\begin{abstract}
JavaScript bundlers are a critical component of modern web development, transforming source modules into optimized production artifacts.
Despite their ubiquity---Staicu et al.\ found that 40\% of websites rely on bundlers---no peer-reviewed empirical comparison of modern bundlers exists.
Existing benchmarks suffer from trivially synthetic projects, vendor maintenance bias, and absence of statistical rigor.

We present the first rigorous empirical comparison of five production-ready JavaScript bundlers---Vite~8, Rspack~2, esbuild~0.28, Webpack~5, and Rollup~4---across 11 directly measured metrics spanning build performance, output quality, and resource consumption.
Our study employs a two-tier benchmarking strategy: Tier~1 uses calibrated synthetic React+TypeScript projects at five scales (50--5{,}000 modules) for controlled comparison; Tier~2 validates findings on a real-world open-source project (Bulletproof React, 102 components).
We apply non-parametric statistics---Kruskal--Wallis omnibus tests, Mann--Whitney $U$ pairwise comparisons with Bonferroni correction, and Cliff's delta effect sizes---to 1{,}534 valid data points.

Results show that tool selection depends on project scale: esbuild is fastest at $\leq$500 modules, while Vite~8 (powered by its Rust-based Rolldown engine) dominates at $\geq$2{,}000 modules, completing a 5{,}000-module production build in 5.9\,s versus 73.5\,s for Webpack.
All five tools exhibit linear build-time scaling ($R^2 \geq 0.97$), with Vite's slope 23.9$\times$ lower than Webpack's.
Of 27 omnibus tests, all are statistically significant ($p < 0.05$); 197 of 205 pairwise comparisons yield large effect sizes.
Tier~2 rankings match Tier~1, supporting external generalizability.
We provide a full replication package.
\end{abstract}

\section{Introduction}\label{sec:intro}

JavaScript bundlers are the invisible infrastructure of modern web development.
They transform thousands of source modules---JavaScript, TypeScript, CSS, images---into optimized bundles that browsers can efficiently load.
Staicu et al.~\cite{staicu2023jackinthebox} found that 40\% of websites rely on bundlers, and the State of JavaScript 2025 survey~\cite{stateofjs2025} reports that $\sim$86\% of developers use Webpack, while Vite has become the most-adopted tool for new projects at $\sim$16 million weekly npm downloads.
The choice of bundler directly impacts developer productivity---build wait times are the primary complaint driving bundler migration---and end-user experience through bundle size, code splitting, and load performance.

Despite this ubiquity, \emph{no peer-reviewed empirical comparison of modern JavaScript bundlers exists}.
The only prior academic work is a Bachelor's thesis~\cite{nguyen2024comparative} comparing just Webpack and Vite on a single project scale with no statistical analysis.
The grey literature---vendor-maintained benchmarks~\cite{rspackbench2026,rolldownbench2026} and blog posts---suffers from three systematic limitations: (1)~trivially synthetic components ($\sim$5 lines of empty JSX); (2)~vendor maintenance bias, where the team maintaining the benchmark also maintains the tool being benchmarked; and (3)~no statistical rigor (single runs or averages of 3 runs, no confidence intervals, no effect sizes).

This paper presents the first rigorous empirical comparison of five production-ready JavaScript bundlers---Vite~8, Rspack~2, esbuild~0.28, Webpack~5, and Rollup~4---spanning three implementation languages (Rust, Go, JavaScript) and three architectural paradigms.
We introduce a \emph{two-tier benchmarking strategy}: Tier~1 uses calibrated synthetic React + TypeScript projects at five scales (50--5{,}000 modules) for controlled comparison; Tier~2 validates on a real-world open-source project (Bulletproof React, 102 components) to confirm external generalizability.

Our contributions are:
\begin{enumerate}[leftmargin=*]
  \item \textbf{Comprehensive empirical dataset}: 1{,}534 valid data points across 5 tools $\times$ 5 scales $\times$ 11 metrics, collected on a controlled single-machine environment.
  \item \textbf{Two-tier benchmarking strategy}: calibrated synthetic projects (50--150 LOC components, 8 template categories, realistic dependency graphs) combined with real-world OSS validation.
  \item \textbf{Statistically rigorous analysis}: non-parametric tests (Kruskal--Wallis, Mann--Whitney $U$ with Bonferroni correction) and Cliff's delta effect sizes, motivated by 64\% non-normality in our data.
  \item \textbf{Actionable findings}: scale-dependent tool selection (esbuild at $\leq$500 modules, Vite at $\geq$2{,}000), linear scaling law ($R^2 \geq 0.97$ for all tools), and 23.9$\times$ slope differences between the fastest and slowest tools.
  \item \textbf{Full replication package}: scripts, raw data, analysis code, and bundler configurations for complete reproducibility.
\end{enumerate}

\section{Background}\label{sec:background}

\subsection{JavaScript Module Systems}

The JavaScript module landscape has evolved through several generations.
Early web development relied on manually ordered \texttt{<script>} tags with global scope pollution.
Node.js introduced CommonJS (2009) with synchronous \texttt{require()} semantics, enabling server-side modularity but remaining incompatible with browsers.
AMD (Asynchronous Module Definition) addressed browser asynchronicity but added configuration complexity.

ECMAScript 2015 standardized ES Modules (ESM)~\cite{ecma2015modules} with static \texttt{import}/\texttt{export} syntax, enabling static analysis for tree-shaking (dead-code elimination) and supporting both browser and server environments~\cite{nodejs2024esm}.
Despite native browser support for ESM, production applications still require bundling for three reasons: (1)~hundreds of HTTP requests for individual modules degrade load performance; (2)~bundlers apply optimizations (minification, code splitting, scope hoisting) that browsers cannot; and (3)~many npm packages still ship only CommonJS, requiring transformation.

\subsection{Bundler Architectures}

Modern JavaScript bundlers follow three architectural paradigms:

\textbf{Fully bundled.}
Tools such as Webpack, esbuild, Rspack, and Rollup bundle all modules into optimized chunks for both development and production.
The development server serves pre-compiled bundles, which increases cold-start time but enables fast hot module replacement (HMR) via granular chunk updates.

\textbf{Unbundled development.}
Vite serves individual ES modules to the browser during development via native ESM, transforming files on demand.
This yields near-instant cold starts regardless of project size (confirmed by our M1 results in Section~\ref{sec:rq1}), but requires a separate production bundling step.

\textbf{Implementation language.}
A key differentiator is whether the bundler's core is implemented in JavaScript (Webpack, Rollup), Go (esbuild), or Rust (Vite/Rolldown, Rspack).
Native-compiled languages avoid the overhead of V8's JIT compilation and garbage collection, enabling parallelism via OS threads (Rust) or goroutines (Go).
This architectural difference is a primary driver of the performance gaps measured in our study.

\subsection{Tools Under Study}

Table~\ref{tab:tools} (Section~\ref{sec:tools}) summarizes the five tools.
Vite~8~\cite{vite2026} is the most-downloaded tool ($\sim$16M weekly) and underwent a major architectural change in version~8, unifying its development and production engines on Rolldown~\cite{rolldown2026}.
Rspack~\cite{rspack2026} offers Webpack API compatibility with a Rust core.
esbuild~\cite{esbuild2026} pioneered the native-speed bundling category.
Webpack~\cite{webpack2026} remains the incumbent with the largest ecosystem.
Rollup~\cite{rollup2026} is a pure-JavaScript baseline that pioneered tree-shaking.
Detailed profiles and selection rationale are provided in Section~\ref{sec:tools}.

\section{Related Work}\label{sec:related}

\subsection{Academic Studies of Build Tools}

Despite the ubiquity of JavaScript bundlers, academic attention to them is remarkably sparse.
The only prior academic work directly comparing JavaScript bundlers is Nguyen~\cite{nguyen2024comparative}, a Bachelor's thesis that compares Webpack and Vite on a single project scale using single-run measurements without statistical analysis.
Our study extends this substantially: five tools, five scales, 11 metrics, 1{,}534 data points, and non-parametric statistics with effect sizes.

In the broader build-systems literature, McIntosh et al.~\cite{mcintosh2015build} conducted an empirical study of build technology (Make, Ant, Maven) and its relationship to software maintenance, finding that build technology choice affects defect-proneness.
Nejati et al.~\cite{nejati2024understanding} studied changes to build systems and their impact on software quality.
Neither addresses JavaScript bundler performance, but both motivate the importance of studying build tooling empirically.

\subsection{Grey Literature and Vendor Benchmarks}

The practical benchmark landscape for JavaScript bundlers is dominated by vendor-maintained repositories.
The rspack-contrib/build-tools-performance benchmark~\cite{rspackbench2026}, maintained by the Rspack team, compares Rspack, Vite, Webpack, and others using a single project with trivially synthetic components ($\sim$5 lines each) and reports averages of three runs without statistical analysis.
The Rolldown benchmarks~\cite{rolldownbench2026}, maintained by the Vite/Rolldown team, focus on module resolution speed with 19{,}000-module synthetic projects.

These benchmarks suffer from three systematic limitations that our study addresses:
(1)~\emph{trivially synthetic components} that do not exercise tree-shaking, CSS processing, or TypeScript generics;
(2)~\emph{vendor maintenance bias}, where the maintaining team has an incentive to optimize for their own tool's strengths;
and (3)~\emph{absence of statistical rigor}---no normality tests, no omnibus comparisons, no effect sizes, and typically only 3 runs averaged.

Blog posts and tech articles (e.g., DEV Community, Tech Insider) provide anecdotal comparisons but use ad-hoc methodology, single runs, and inconsistent configurations, making their findings unreliable for scientific conclusions.

\subsection{Performance Benchmarking Methodology}

Our methodological design draws on several established benchmarking frameworks.
Kalibera and Jones~\cite{kalibera2013rigorous} formalized rigorous benchmarking, introducing cost models for variance analysis and arguing that benchmarks must report confidence intervals and effect sizes---practices we follow throughout.
Georges et al.~\cite{georges2007statistically} demonstrated that statistically rigorous evaluation of Java performance requires multiple invocations with proper warm-up handling, motivating our 10--20 runs per configuration and use of the median.
Barrett et al.~\cite{barrett2017vm} showed that 43.5\% of VM+benchmark pairs fail to reach steady state, supporting our decision to use the median rather than assuming steady-state convergence.

In the systems software domain, Henning and Hasselbring~\cite{henning2024benchmarking} (published in JSS) presented Theodolite, a systematic method for benchmarking scalability of stream processing frameworks.
Their approach---controlled synthetic workloads, scaling analysis across multiple dimensions, and statistical comparison---directly inspired our two-tier design and scaling regression analysis.
Mohan and Goswami~\cite{mohan2025nodejs} compared Node.js and Java Spring Boot for RESTful API performance in SPE, providing a structural model for tool-comparison papers in software engineering journals.

\section{Study Design}\label{sec:design}

This section describes the design of our empirical study, following the guidelines of Wohlin et al.~\cite{wohlin2012experimentation} and Kitchenham et al.~\cite{kitchenham2002preliminary}, and the benchmarking methodology established by Kalibera and Jones~\cite{kalibera2013rigorous} and Jain~\cite{jain1991art}.

\subsection{Research Questions}\label{sec:rqs}

We structure our investigation around three research questions, each addressing a distinct dimension of bundler performance.

\medskip\noindent\textbf{RQ1: How do modern JavaScript bundlers compare in build performance across project scales?}
Build speed directly impacts developer productivity and is the primary reason teams migrate bundlers~\cite{stateofjs2025}.
We measure four metrics: development server cold-start time (M1), production build time (M2), incremental rebuild latency (M3), and hot module replacement (HMR) latency (M4).

\medskip\noindent\textbf{RQ2: How does bundler choice affect output quality and delivery efficiency?}
A fast bundler that produces bloated output is a false economy; bundle size and code-splitting granularity directly affect end-user load times.
We measure raw bundle size (M5), gzipped bundle size (M6), tree-shaking effectiveness (M7), code-splitting granularity (M8), and sourcemap accuracy (M9).

\medskip\noindent\textbf{RQ3: How do resource consumption and scaling behavior differ across bundlers?}
Resource usage determines viability in CI/CD environments with memory limits and on developer machines with 8--32\,GB RAM.
We measure peak resident-set-size memory (M10), CPU time (M11), and derive scaling regression models from M2 across all five project scales (M12).

\subsection{Tool Selection}\label{sec:tools}

We select five tools spanning three architectural paradigms and three implementation languages, ensuring a balanced comparison.
The inclusion criteria are: (1)~open source and installable via npm; (2)~standalone (usable outside a specific framework); (3)~production-ready with stable release; (4)~significant adoption ($\geq$100K weekly npm downloads or major organizational backing); and (5)~architecturally distinct from other selected tools.

\textbf{Vite~8}~\cite{vite2026} represents the dominant greenfield choice ($\sim$16M weekly downloads). Version~8 is architecturally significant: it replaced both esbuild (development transforms) and Rollup (production bundling) with Rolldown~\cite{rolldown2026}, a unified Rust-based engine---a fundamental shift worth quantifying.

\textbf{Rspack~2}~\cite{rspack2026}, developed by ByteDance, offers a drop-in Webpack replacement with a Rust core. It represents the ``migrate existing Webpack projects to Rust'' migration path and tests whether API compatibility incurs a performance cost.

\textbf{esbuild~0.28}~\cite{esbuild2026}, written in Go, pioneered the 10--100$\times$ speedup narrative that catalyzed the Rust/Go bundler wave. Its minimal plugin API tests the raw-speed-versus-extensibility tradeoff. As the only Go-based tool, it provides a cross-language comparison point.

\textbf{Webpack~5}~\cite{webpack2026} is the incumbent, used by $\sim$86\% of developers~\cite{stateofjs2025}. We equip it with SWC~\cite{swc2026} for Rust-accelerated transforms, giving it the best-case scenario. It serves as the \emph{baseline control}.

\textbf{Rollup~4}~\cite{rollup2026}, Vite's former production engine, is a pure-JavaScript ESM-native bundler. It serves as the \emph{second baseline}, establishing the performance floor of a tool without Rust or Go acceleration.

\medskip\noindent\textbf{Excluded tools.} Turbopack lacks a stable standalone production build (it functions only as a Next.js-internal development bundler) and is noted as future work. Parcel~2 overlaps architecturally with Vite. Farm has insufficient adoption ($\sim$2K GitHub stars). Bun's bundler is runtime-integrated (different execution model). SWC is a transpiler, not a full bundler.

\subsection{Two-Tier Benchmarking Strategy}\label{sec:twotier}

A key design decision is how to construct the projects being benchmarked.
Existing vendor-maintained benchmarks (e.g., rspack-contrib/build-tools-performance~\cite{rspackbench2026}, Rolldown benchmarks~\cite{rolldownbench2026}) use trivially synthetic components ($\sim$5 lines of empty JSX), while purely real-world projects cannot be fairly ported to all five bundlers due to bundler-specific APIs.
Our solution is a \textbf{two-tier strategy} that satisfies both internal validity (controlled comparison via synthetic projects) and external validity (real-world generalizability).

\subsection{Measurement Harness}\label{sec:harness}

All experiments were conducted on a single machine to eliminate hardware variability: Apple M2~Pro (12-core, 32\,GB RAM) running macOS~26.5, Node.js~v22.16.0, and npm~10.9.2.
Background processes were minimized during all measurement runs.

\textbf{M2 (production build time)} is measured using hyperfine~\cite{hyperfine2024}, a command-line benchmarking tool that reports per-run wall-clock times.
Before each run, a cache-clearing script removes \texttt{node\_modules/.cache}, \texttt{dist/}, \texttt{.rspack/}, \texttt{.vite/}, and OS filesystem caches where applicable.
We configure hyperfine with zero explicit warm-up runs (\texttt{--warmup 0}) and 10 measured runs (\texttt{--runs 10}).

\textbf{M1 (dev cold start)} is measured by starting the development server process, monitoring \texttt{stdout} for the tool-specific ``ready'' pattern (e.g., \texttt{"Local:"} for Vite, \texttt{"compiled"} for Webpack/Rspack), and recording the elapsed wall-clock time.
This is repeated for 20 independent runs with cache clearing between each.
A 60-second timeout classifies non-responding servers as failures.

\textbf{M3 (incremental rebuild)} uses each tool's \texttt{build --watch} mode.
A dedicated Node.js script starts the watch process, waits for the initial build to complete, then programmatically modifies a randomly selected component file (toggling a JSX attribute) and measures the time until the watcher reports rebuild completion.
This is repeated for 20 file changes per configuration.

\textbf{M4 (HMR latency)} is measured via Puppeteer~\cite{puppeteer2024} controlling a headless Chromium browser.
The script launches the development server, navigates Puppeteer to the local URL, intercepts Chrome DevTools Protocol (CDP) console messages, then modifies a component file.
The HMR latency is the interval between the file-system write and the browser console's HMR confirmation message.
This is repeated for 20 independent file modifications.

\textbf{M5--M9 (output quality)} are deterministic single-run metrics computed from the production build output.
Each is verified by a second independent build to confirm determinism.
M5 sums all file sizes in the output directory; M6 applies \texttt{gzip -9} to each JavaScript file and sums; M7 counts residual \texttt{lodash-es} references (full library is $\sim$600\,KB; our code imports only \texttt{pick} and \texttt{debounce}); M8 counts distinct JavaScript chunks; M9 reports the ratio of sourcemap files to JavaScript files.

\textbf{M10 and M11 (memory and CPU)} are extracted from the macOS \texttt{command time -l} utility, which reports peak resident set size (in bytes) and user + system CPU time.
Ten independent runs are performed with cache clearing between each.

\textbf{No explicit warm-up.} Following Barrett et al.~\cite{barrett2017vm}, who showed that 43.5\% of VM+benchmark pairs fail to reach steady state, we do not assume warm-up convergence. Instead, we use the median (robust to outliers) as our primary summary statistic and report the full interquartile range.

\subsection{Statistical Analysis}\label{sec:stats}

Our statistical pipeline follows the recommendations of Georges et al.~\cite{georges2007statistically} for non-parametric analysis of performance data.

\textbf{Step 1: Normality testing.}
We apply the Shapiro--Wilk test~\cite{shapiro1965analysis} ($\alpha = 0.05$) to every tool$\times$size$\times$metric group with $n \geq 3$.
Of the 115 testable groups, 74 (64\%) reject the null hypothesis of normality, motivating non-parametric methods throughout.

\textbf{Step 2: Omnibus test.}
For each metric$\times$size combination where multiple tools have data, we apply the Kruskal--Wallis $H$ test~\cite{kruskal1952use} ($\alpha = 0.05$) to determine whether at least one tool differs significantly from the others.

\textbf{Step 3: Pairwise comparisons.}
Where the omnibus test is significant, we conduct all $\binom{k}{2}$ pairwise Mann--Whitney $U$ tests~\cite{mann1947test} with Bonferroni correction~\cite{bonferroni1936teoria} to control the family-wise error rate.

\textbf{Step 4: Effect sizes.}
For every pairwise comparison, we compute Cliff's delta~\cite{cliff1993dominance}, a non-parametric effect-size measure interpreted as: $|\delta| < 0.147$ (negligible), $< 0.33$ (small), $< 0.474$ (medium), and $\geq 0.474$ (large), following the thresholds of Vargha and Delaney~\cite{vargha2000critique}.

\textbf{Step 5: Scaling regression.}
For each tool, we fit both a linear model ($\text{build\_time} = a \cdot \text{modules} + b$) and a log-linear model ($\text{build\_time} = a \cdot \ln(\text{modules}) + b$) to the five Tier~1 M2 medians.
We select the model with the higher $R^2$.

All analysis code is implemented in TypeScript (executed via \texttt{tsx}) using the \texttt{simple-statistics} library and is included in the replication package.

In watch mode, Webpack is the fastest at the smallest scale (138\,ms at xs-50), with Rspack close behind (188\,ms).

esbuild is excluded from M3 as it lacks a native watch mode.

\subsubsection{M4: HMR Latency}

Rspack and Webpack achieve near-identical HMR latencies: 14\,ms at both xs-50 and m-500 for both tools, with negligible-to-small Cliff's delta values between them ($|\delta| = 0.34$ at xs-50, $|\delta| = 0.15$ at m-500).
Vite's HMR is slower at 76\,ms (m-500) and 132\,ms (xs-50, $n = 3$).
This is unexpected given Vite's native ESM architecture; the overhead likely stems from Vite's HMR protocol requiring a full module graph traversal, whereas Rspack and Webpack use direct chunk replacement.

\medskip\noindent\textbf{Finding 1.} \textit{Build tool selection for speed depends on project scale. esbuild dominates at $\leq$500 modules; Vite dominates at $\geq$2{,}000 modules. For incremental development, Rspack and Webpack offer the fastest watch-mode rebuilds and HMR, while Vite's dev server cold-start is uniquely scale-invariant.}

\section{Discussion}\label{sec:discussion}

\subsection{Key Findings Summary}\label{sec:findings}

Our study yields four principal findings that collectively demonstrate there is no single ``best'' JavaScript bundler---the optimal choice depends on project scale and priorities.

\begin{enumerate}[leftmargin=*,label=\textbf{F\arabic*.}]
  \item \textbf{Scale-dependent build-speed leadership.} esbuild is fastest at $\leq$500 modules; Vite is fastest at $\geq$2{,}000 modules. The crossover occurs between 500 and 2{,}000 modules.
  \item \textbf{Output quality is a secondary differentiator.} While bundle sizes and tree-shaking effectiveness vary across tools, these differences are smaller in practical impact than the order-of-magnitude build-speed differences.
  \item \textbf{Linear scaling with dramatic slope differences.} All tools scale linearly ($R^2 \geq 0.97$), but Vite's slope (954\,ms / 1{,}000 modules) is 23.9$\times$ lower than Webpack's (22{,}770\,ms / 1{,}000 modules). Implementation language---Rust/Go versus JavaScript---is the primary determinant.
  \item \textbf{Two-tier validation.} Tier~2 (real-world OSS) rankings match Tier~1 (synthetic) for M2 and M10, with only one negligible adjacent-rank swap for M11, supporting external generalizability.
\end{enumerate}

\subsection{Practical Implications}\label{sec:practical}

Based on our findings, we propose the decision framework in Table~\ref{tab:decision}.

\textbf{Rspack as a Webpack migration path.}
Teams with existing Webpack projects face a meaningful upgrade path: Rspack's Webpack-compatible API enables migration without rewriting build configurations, while delivering a 4.3--8.4$\times$ build-speed improvement across our tested scales.
At m-500, Rspack builds in 2{,}516\,ms versus Webpack's 10{,}982\,ms---a 4.4$\times$ improvement.
At xl-5{,}000, the improvement grows to 8.4$\times$ (13{,}848\,ms vs.\ 115{,}872\,ms).

\textbf{The Vite~8 architectural shift.}
Vite~8's replacement of both esbuild and Rollup with a single Rolldown engine is quantifiably beneficial.
Vite achieves the lowest scaling slope (954\,ms / 1{,}000 modules) while also producing the smallest gzipped bundles---a combination of build speed and output quality unmatched by other tools.
The scale-invariant dev cold start ($\sim$865\,ms regardless of project size) further supports Vite's suitability for large projects.

\subsection{Architectural Insights}\label{sec:arch}

\textbf{Implementation language matters---but architecture matters more.}
The three fastest build tools at large scale are all Rust-based or Go-based (Vite/Rolldown, Rspack, esbuild), while the two slowest are JavaScript-based (Rollup, Webpack).
However, Vite (Rust) is 2.5$\times$ faster than esbuild (Go) at xl-5{,}000, suggesting that Rust's zero-cost abstractions and parallelism model provide an advantage over Go's goroutine-based concurrency for this workload.

\textbf{Rollup's scalability ceiling.}
Rollup's CPU time explodes from 15\,s (m-500) to 1{,}737\,s (xl-5{,}000), a 116$\times$ increase versus the expected 10$\times$ from linear scaling.
This super-linear CPU behavior---despite linear wall-clock build time ($R^2 = 0.973$)---indicates that Rollup compensates with heavy single-thread CPU utilization.
The root cause is Rollup's exhaustive Temporal Dead Zone (TDZ) analysis during scope hoisting, which becomes quadratic in the number of cross-module references.

\textbf{Watch-mode degradation at enterprise scale.}
At xl-5{,}000, only one tool (Vite) successfully completed an incremental rebuild in watch mode, and even that took 16.5\,s for a single file change.
This represents an industry-wide gap: none of the five tools provide sub-second incremental rebuilds at enterprise scale, despite all achieving this at smaller scales.

\subsection{Comparison with Grey Literature}\label{sec:grey}

Our findings qualitatively agree with vendor benchmarks in ranking direction but diverge in magnitude.
The rspack-contrib benchmark~\cite{rspackbench2026} reports Vite's production build as the fastest among the tools we study---consistent with our findings at $\geq$2{,}000 modules but not at smaller scales, where esbuild leads.
The divergence arises because vendor benchmarks typically use a single, small project scale, missing the crossover phenomenon that is our central finding.

Both vendor benchmarks and our study rank Webpack and Rollup as the slowest tools.
However, our measurements show larger performance gaps than vendor benchmarks report (e.g., 19.7$\times$ for Webpack vs.\ Vite at xl-5{,}000, compared to $\sim$10$\times$ in vendor data), likely because our calibrated synthetic projects---with 50--150 LOC components, realistic imports, and CSS Modules---exercise more bundler subsystems than the trivial 5-line components used in vendor benchmarks.

\section{Threats to Validity}\label{sec:threats}

We discuss threats following the four-category framework of Wohlin et al.~\cite{wohlin2012experimentation}.

\subsection{Internal Validity}

\textbf{Single machine.}
All experiments were conducted on a single Apple M2~Pro machine.
While this eliminates hardware variability, it limits generalizability to other architectures (x86, ARM server, CI runners).
We mitigate this by reporting relative rankings (which are less hardware-sensitive than absolute times) and note multi-platform benchmarking as future work.

\textbf{Run~1 cold-start effect.}
The first run of a benchmark session may exhibit inflated times due to OS-level caching, JIT compilation, or disk I/O.
We mitigate this by using the \emph{median} (which is robust to outliers) as our primary statistic, clearing caches before every run, and reporting IQR to quantify variability.
Notably, our data audit identified this effect in the Rollup M2 data, where we discarded a pilot batch exhibiting 13.9\,s first-run inflation.

\textbf{Measurement precision.}
Wall-clock timing via hyperfine (M2) and Node.js \texttt{Date.now()} (M1, M3, M4) has millisecond precision.
For measurements in the range of hundreds of milliseconds to minutes, this precision is sufficient.
The tight IQRs observed (e.g., 35\,ms for esbuild M2 at m-500, $n = 10$) confirm low measurement noise.

\subsection{External Validity}

\textbf{Synthetic projects.}
Despite our calibration effort (8 component templates, 50--150 LOC, realistic patterns), synthetic projects may not capture all characteristics of production codebases.
We mitigate this with the two-tier design: Tier~2 (Bulletproof React) validates that Tier~1 rankings generalize.
The exact ranking match for M2 and M10 (Table~\ref{tab:tier2}) supports this mitigation.

\textbf{Single real-world project.}
Tier~2 uses only one OSS project (Bulletproof React, 102 files).
A broader validation with multiple projects of varying size, framework (Vue, Angular, Svelte), and complexity would strengthen external validity.
We note this as future work.

\textbf{React + TypeScript only.}
All projects use React and TypeScript, the most popular frontend framework and language~\cite{stateofjs2025}.
Results may differ for other frameworks due to different plugin pipelines and transform requirements.

\textbf{Tool versions.}
All tool versions were pinned on experiment Day~1.
Bundler performance improves across releases; our results reflect the state as of September 2026.

\subsection{Construct Validity}

\textbf{Metric coverage.}
Our 11 metrics cover build speed, output quality, and resource consumption, but do not measure developer experience factors such as error message quality, configuration complexity, plugin ecosystem breadth, or IDE integration.
These are qualitatively important but require different research methods (e.g., surveys, usability studies).

\textbf{M1 limited coverage.}
Dev cold start (M1) was measurable for only 2 of 5 tools (Vite and Webpack); Rspack timed out at all sizes.
We report this limitation explicitly and treat the timeout as a finding rather than missing data.

\textbf{HMR measurement.}
M4 captures HMR latency via Chrome DevTools Protocol console interception, which measures the time from file change to browser-side confirmation.
This may miss sub-component updates that do not produce console output, potentially underestimating HMR overhead for partial updates.

\textbf{Tree-shaking metric.}
M7 counts residual \texttt{lodash-es} references, which is a proxy for tree-shaking effectiveness.
Different tools may inline, rename, or split lodash utilities differently, making exact comparisons imperfect.
However, the metric consistently distinguishes tools that include the full library from those that eliminate unused exports.

\subsection{Conclusion Validity}

\textbf{Non-parametric statistics.}
Given that 64\% of groups are non-normal, our use of Kruskal--Wallis and Mann--Whitney $U$ tests is appropriate.
These tests are less powerful than parametric alternatives, meaning we may underestimate the number of significant differences.

\textbf{Bonferroni correction.}
The Bonferroni correction is conservative and may produce false negatives for borderline comparisons.
Of 205 pairwise tests, 17 are non-significant after correction; all involve adjacent-ranked tools with small absolute differences.
Using a less conservative correction (e.g., Holm--Bonferroni) would likely make several of these significant without changing our overall conclusions.

\textbf{Sample sizes.}
With $n = 10$ runs for M2/M10/M11 and $n = 20$ for M1/M3/M4, our sample sizes are sufficient to detect the large effects observed (197 of 205 pairs show large Cliff's delta).
All 27 Kruskal--Wallis tests are significant, confirming adequate statistical power.

\section{Conclusion and Future Work}\label{sec:conclusion}

We presented the first peer-reviewed empirical comparison of five production-ready JavaScript bundlers---Vite~8, Rspack~2, esbuild~0.28, Webpack~5, and Rollup~4---across 11 directly measured metrics and five project scales (50--5{,}000 modules).
Our two-tier benchmarking strategy combined calibrated synthetic projects (Tier~1) with a real-world open-source application (Tier~2), and our statistical analysis applied non-parametric tests with effect sizes to 1{,}534 valid data points.

The central finding is that \emph{there is no single fastest bundler}: esbuild leads at small scales ($\leq$500 modules), while Vite~8 dominates at large scales ($\geq$2{,}000 modules) with a scaling slope 23.9$\times$ lower than Webpack's.
All tools scale linearly ($R^2 \geq 0.97$), and Tier~2 rankings match Tier~1, validating our synthetic project design.
For practitioners, we provide an actionable decision matrix (Table~\ref{tab:decision}) based on project scale and priorities.

\medskip\noindent\textbf{Future work.}
\begin{enumerate}[leftmargin=*]
  \item \textbf{Multi-platform benchmarking} on Linux CI runners, x86 servers, and ARM cloud instances to test hardware generalizability.
  \item \textbf{Turbopack} once a stable standalone production build is available outside Next.js.
  \item \textbf{Longitudinal study} tracking performance changes across bundler versions over 12--18 months.
  \item \textbf{Framework diversity}: replicating the study with Vue, Angular, and Svelte projects.
  \item \textbf{Additional Tier~2 projects} of varying size and complexity to strengthen external validity.
  \item \textbf{Developer experience metrics}: error message quality, configuration complexity, and plugin ecosystem analysis via surveys and usability studies.
\end{enumerate}
