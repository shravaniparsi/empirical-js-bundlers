\begin{abstract}
JavaScript bundlers are a critical component of modern web development, transforming source modules into optimized production artifacts.
Despite their ubiquity---Staicu et al.\ found that 40\% of websites rely on bundlers---no peer-reviewed empirical comparison of modern bundlers exists.
Existing benchmarks suffer from trivially synthetic projects, vendor maintenance bias, and absence of statistical rigor.

We present, to our knowledge, the first rigorous empirical comparison of five production-ready JavaScript bundlers---Vite~8, Rspack~2, esbuild~0.28, Webpack~5, and Rollup~4---across 11 directly measured metrics spanning build performance, output quality, and resource consumption.
Our study employs a two-tier benchmarking strategy: Tier~1 uses calibrated synthetic React+TypeScript projects at five scales (50--5{,}000 modules) for controlled comparison; Tier~2 evaluates which findings replicate on one real-world open-source project (Bulletproof React, 102 components).
We analyze 1{,}945 observations (1{,}390 analysis units; 1{,}265 entering inferential tests) using tie-corrected Kruskal--Wallis tests, Dunn post-hoc comparisons with Bonferroni correction, and Cliff's delta with bootstrap confidence intervals.

Results show scale-dependent production performance: esbuild has the lowest median through 2{,}000 modules, while Vite~8 has the lowest median at 5{,}000 modules (5.56\,s versus 121.52\,s for Webpack).
Rspack records the lowest incremental-rebuild median at every scale, whereas Vite records the lowest HMR median.
Leave-one-size-out model selection favors linear scaling for Vite and Rspack but quadratic scaling for esbuild, Rollup, and Webpack.
All 30 omnibus tests are significant; 126 of 251 Bonferroni-adjusted Dunn comparisons are significant and 250 of 251 Cliff's delta estimates are large.
Tier~2 broadly preserves the performance tiers but includes adjacent-rank changes, bounding rather than proving external validity.
We provide a full replication package.
\end{abstract}

\section{Introduction}\label{sec:intro}

JavaScript bundlers are the invisible infrastructure of modern web development.
They transform thousands of source modules---JavaScript, TypeScript, CSS, images---into optimized bundles that browsers can efficiently load.
Staicu et al.~\cite{staicu2023jackinthebox} found that 40\% of websites rely on bundlers, and the State of JavaScript 2025 survey~\cite{stateofjs2025} reports that $\sim$86\% of developers use Webpack, while Vite has become the most-adopted tool for new projects at $\sim$16 million weekly npm downloads.
The choice of bundler directly impacts developer productivity---build wait times are the primary complaint driving bundler migration---and end-user experience through bundle size, code splitting, and load performance.

Despite this ubiquity, \emph{no peer-reviewed empirical comparison of modern JavaScript bundlers exists}.
The only prior academic work is a Bachelor's thesis~\cite{nguyen2024comparative} comparing just Webpack and Vite on a single project scale with no statistical analysis.
The grey literature---vendor-maintained benchmarks~\cite{rspackbench2026,rolldownbench2026} and blog posts---suffers from three systematic limitations: (1)~trivially synthetic components ($\sim$5 lines of empty JSX); (2)~vendor maintenance bias, where the team maintaining the benchmark also maintains the tool being benchmarked; and (3)~no statistical rigor (single runs or averages of 3 runs, no confidence intervals, no effect sizes).

This paper presents what is, to our knowledge, the first rigorous empirical comparison of five production-ready JavaScript bundlers---Vite~8, Rspack~2, esbuild~0.28, Webpack~5, and Rollup~4---spanning three implementation languages (Rust, Go, JavaScript) and three architectural paradigms.
We introduce a \emph{two-tier benchmarking strategy}: Tier~1 uses calibrated synthetic React + TypeScript projects at five scales (50--5{,}000 modules) for controlled comparison; Tier~2 evaluates whether principal findings persist on a real-world open-source project (Bulletproof React, 102 components).

Our contributions are:
\begin{enumerate}[leftmargin=*]
  \item \textbf{Comprehensive empirical dataset}: 1{,}945 observations across 5 tools, 5 synthetic scales, and 11 directly measured metrics, collected in a controlled single-machine environment.
  \item \textbf{Two-tier benchmarking strategy}: calibrated synthetic projects (50--150 LOC components, 8 template categories, realistic dependency graphs) combined with scoped real-world OSS replication.
  \item \textbf{Statistically rigorous analysis}: tie-corrected Kruskal--Wallis tests, Dunn comparisons with within-family Bonferroni correction, Cliff's delta with deterministic bootstrap intervals, and session-level units for repeated M3/M4 updates.
  \item \textbf{Actionable findings}: scale-dependent production performance, Rspack's low incremental-rebuild latency, Vite's low browser-observed HMR latency, and substantially lower resource use by esbuild.
  \item \textbf{Full replication package}: scripts, raw data, analysis code, and bundler configurations for complete reproducibility.
\end{enumerate}

\section{Background}\label{sec:background}

\subsection{JavaScript Module Systems}

The JavaScript module landscape has evolved through several generations.
Early web development relied on manually ordered \texttt{<script>} tags with global scope pollution.
Node.js introduced CommonJS (2009) with synchronous \texttt{require()} semantics, enabling server-side modularity but remaining incompatible with browsers.
AMD (Asynchronous Module Definition) addressed browser asynchronicity but added configuration complexity.

ECMAScript 2015 standardized ES Modules (ESM)~\cite{ecma2015modules} with static \texttt{import}/\texttt{export} syntax, enabling static analysis for tree-shaking (dead-code elimination) and supporting both browser and server environments~\cite{nodejs2024esm}.
Despite native browser support for ESM, production applications still require bundling for three reasons: (1)~hundreds of HTTP requests for individual modules degrade load performance; (2)~bundlers apply optimizations (minification, code splitting, scope hoisting) that browsers cannot; and (3)~many npm packages still ship only CommonJS, requiring transformation.

\subsection{Bundler Architectures}

Modern JavaScript bundlers follow three architectural paradigms:

\textbf{Fully bundled.}
Tools such as Webpack, esbuild, Rspack, and Rollup bundle all modules into optimized chunks for both development and production.
The development server serves pre-compiled bundles, which increases cold-start time but enables fast hot module replacement (HMR) via granular chunk updates.

\textbf{Unbundled development.}
Vite serves individual ES modules to the browser during development via native ESM, transforming files on demand.
This yields near-instant cold starts regardless of project size (confirmed by our M1 results in Section~\ref{sec:rq1}), but requires a separate production bundling step.

\textbf{Implementation language.}
A key differentiator is whether the bundler's core is implemented in JavaScript (Webpack, Rollup), Go (esbuild), or Rust (Vite/Rolldown, Rspack).
Native-compiled implementations can avoid portions of V8's JIT and garbage-collection overhead and can exploit native threading models.
Implementation language is nevertheless confounded with algorithms, defaults, plugin pipelines, and architecture; our observational design cannot attribute measured differences to language alone.

\subsection{Tools Under Study}

The five tools are profiled in Section~\ref{sec:tools}.
Vite~8~\cite{vite2026} is the most-downloaded tool ($\sim$16M weekly) and underwent a major architectural change in version~8, unifying its development and production engines on Rolldown~\cite{rolldown2026}.
Rspack~\cite{rspack2026} offers Webpack API compatibility with a Rust core.
esbuild~\cite{esbuild2026} pioneered the native-speed bundling category.
Webpack~\cite{webpack2026} remains the incumbent with the largest ecosystem.
Rollup~\cite{rollup2026} is a pure-JavaScript baseline that pioneered tree-shaking.
Detailed profiles and selection rationale are provided in Section~\ref{sec:tools}.

\section{Related Work}\label{sec:related}

We conducted a systematic literature search on August~28, 2026 across four databases: ACM Digital Library, IEEE Xplore, Scopus, and Google Scholar.
We used two query strings: (Q1)~\texttt{"javascript bundler" AND (benchmark OR performance OR comparison)} and (Q2)~\texttt{(webpack OR vite OR esbuild OR rollup OR rspack) AND "empirical study"}, restricting results to January 2015--August 2026.

\textbf{Inclusion criteria:} (I1)~directly compares at least two JavaScript bundlers; (I2)~reports quantitative performance measurements; (I3)~written in English.
\textbf{Exclusion criteria:} (E1)~pure opinion or tutorial content with no measurement data; (E2)~compares non-bundler tools (e.g., linters, formatters); (E3)~duplicates across databases.

Q1 returned 23 results (ACM: 4, IEEE: 2, Scopus: 3, Scholar: 14); Q2 returned 31 results (ACM: 2, IEEE: 1, Scopus: 5, Scholar: 23).
After deduplication (38 unique), title--abstract screening eliminated 29 papers (E1: 18, E2: 8, E3: 3).
Full-text review of the remaining 9 papers retained 1 that met all inclusion criteria.
We also performed forward and backward citation tracking on all 9 full-text candidates, yielding no additional hits.
The sole qualifying work is Nguyen~\cite{nguyen2024comparative}.

\subsection{Academic Studies of Build Tools}

Despite the ubiquity of JavaScript bundlers, academic attention to them is remarkably sparse.
The only prior academic work directly comparing JavaScript bundlers is Nguyen~\cite{nguyen2024comparative}, a Bachelor's thesis that compares Webpack and Vite on a single project scale using single-run measurements without statistical analysis.
Our study extends this substantially: five tools, five scales, 11 metrics, 1{,}945 raw observations, and non-parametric statistics with effect sizes.

In the broader build-systems literature, McIntosh et al.~\cite{mcintosh2015build} conducted an empirical study of build technology (Make, Ant, Maven) and its relationship to software maintenance, finding that build technology choice affects defect-proneness.
Nejati et al.~\cite{nejati2024understanding} studied changes to build systems and their impact on software quality.
Neither addresses JavaScript bundler performance, but both motivate the importance of studying build tooling empirically.

\subsection{Grey Literature and Vendor Benchmarks}

The practical benchmark landscape for JavaScript bundlers is dominated by vendor-maintained repositories.
The rspack-contrib/build-tools-performance benchmark~\cite{rspackbench2026}, maintained by the Rspack team, compares Rspack, Vite, Webpack, and others using a single project with trivially synthetic components ($\sim$5 lines each) and reports averages of three runs without statistical analysis.
The Rolldown benchmarks~\cite{rolldownbench2026}, maintained by the Vite/Rolldown team, focus on module resolution speed with 19{,}000-module synthetic projects.

These benchmarks suffer from three systematic limitations that our study addresses:
(1)~\emph{trivially synthetic components} that do not exercise tree-shaking, CSS processing, or TypeScript generics;
(2)~\emph{vendor maintenance bias}, where the maintaining team has an incentive to optimize for their own tool's strengths;
and (3)~\emph{absence of statistical rigor}---no normality tests, no omnibus comparisons, no effect sizes, and typically only 3 runs averaged.

Blog posts and tech articles (e.g., DEV Community, Tech Insider) provide anecdotal comparisons but use ad-hoc methodology, single runs, and inconsistent configurations, making their findings unreliable for scientific conclusions.

\subsection{Performance Benchmarking Methodology}

Our methodological design draws on several established benchmarking frameworks.
Kalibera and Jones~\cite{kalibera2013rigorous} formalized rigorous benchmarking, introducing cost models for variance analysis and arguing that benchmarks must report uncertainty and effect sizes---practices we follow through IQRs and Cliff's delta with bootstrap confidence intervals.
Georges et al.~\cite{georges2007statistically} demonstrated that statistically rigorous evaluation of Java performance requires multiple invocations with proper warm-up handling, motivating our 10--20 runs per configuration and use of the median.
Barrett et al.~\cite{barrett2017vm} showed that 43.5\% of VM+benchmark pairs fail to reach steady state, supporting our decision to use the median rather than assuming steady-state convergence.

In the systems software domain, Henning and Hasselbring~\cite{henning2024benchmarking} (published in JSS) presented Theodolite, a systematic method for benchmarking scalability of stream processing frameworks.
Their approach---controlled synthetic workloads, scaling analysis across multiple dimensions, and statistical comparison---directly inspired our two-tier design and scaling regression analysis.
Mohan and Goswami~\cite{mohan2025nodejs} compared Node.js and Java Spring Boot for RESTful API performance in SPE, providing a structural model for tool-comparison papers in software engineering journals.

\section{Study Design}\label{sec:design}

This section describes the design of our empirical study, following the guidelines of Wohlin et al.~\cite{wohlin2012experimentation} and Kitchenham et al.~\cite{kitchenham2002preliminary}, and the benchmarking methodology established by Kalibera and Jones~\cite{kalibera2013rigorous} and Jain~\cite{jain1991art}.

\subsection{Research Questions}\label{sec:rqs}

We structure our investigation around three research questions, each addressing a distinct dimension of bundler performance.

\medskip\noindent\textbf{RQ1: How do modern JavaScript bundlers compare in build performance across project scales?}
Build speed directly impacts developer productivity and is the primary reason teams migrate bundlers~\cite{stateofjs2025}.
We measure four metrics: development server cold-start time (M1), production build time (M2), incremental rebuild latency (M3), and hot module replacement (HMR) latency (M4).

\medskip\noindent\textbf{RQ2: How does bundler choice affect output quality and delivery efficiency?}
A fast bundler that produces bloated output is a false economy; bundle size and code-splitting granularity directly affect end-user load times.
We measure raw bundle size (M5), gzipped bundle size (M6), tree-shaking effectiveness (M7), code-splitting granularity (M8), and sourcemap coverage (M9).

\medskip\noindent\textbf{RQ3: How do resource consumption and scaling behavior differ across bundlers?}
Resource usage determines viability in CI/CD environments with memory limits and on developer machines with 8--32\,GB RAM.
We measure peak resident-set-size memory (M10), CPU-time energy proxy (M11), and derive scaling models from M2 across all five project scales (M12).

\subsection{Tool Selection}\label{sec:tools}

We select five tools spanning three architectural paradigms and three implementation languages, ensuring a balanced comparison.
The inclusion criteria are: (1)~open source and installable via npm; (2)~standalone (usable outside a specific framework); (3)~production-ready with stable release; (4)~significant adoption ($\geq$100K weekly npm downloads or major organizational backing); and (5)~architecturally distinct from other selected tools.

\textbf{Vite~8}~\cite{vite2026} represents the dominant greenfield choice ($\sim$16M weekly downloads). Version~8 is architecturally significant: it replaced both esbuild (development transforms) and Rollup (production bundling) with Rolldown~\cite{rolldown2026}, a unified Rust-based engine---a fundamental shift worth quantifying.

\textbf{Rspack~2}~\cite{rspack2026}, developed by ByteDance, offers a drop-in Webpack replacement with a Rust core. It represents the ``migrate existing Webpack projects to Rust'' migration path and tests whether API compatibility incurs a performance cost.

\textbf{esbuild~0.28}~\cite{esbuild2026}, written in Go, pioneered the 10--100$\times$ speedup narrative that catalyzed the Rust/Go bundler wave. Its minimal plugin API tests the raw-speed-versus-extensibility tradeoff. As the only Go-based tool, it provides a cross-language comparison point.

\textbf{Webpack~5}~\cite{webpack2026} is the incumbent, used by $\sim$86\% of developers~\cite{stateofjs2025}. We equip it with SWC~\cite{swc2026} for Rust-accelerated transforms, giving it the best-case scenario. It serves as the \emph{baseline control}.

\textbf{Rollup~4}~\cite{rollup2026}, Vite's former production engine, is a pure-JavaScript ESM-native bundler. It serves as the \emph{second baseline}, establishing the performance floor of a tool without Rust or Go acceleration.

\medskip\noindent\textbf{Excluded tools.} Turbopack lacks a stable standalone production build (it functions only as a Next.js-internal development bundler) and is noted as future work. Parcel~2 overlaps architecturally with Vite. Farm has insufficient adoption ($\sim$2K GitHub stars). Bun's bundler is runtime-integrated (different execution model). SWC is a transpiler, not a full bundler.

\subsection{Two-Tier Benchmarking Strategy}\label{sec:twotier}

A key design decision is how to construct the projects being benchmarked.
Existing vendor-maintained benchmarks (e.g., rspack-contrib/build-tools-performance~\cite{rspackbench2026}, Rolldown benchmarks~\cite{rolldownbench2026}) use trivially synthetic components ($\sim$5 lines of empty JSX), while purely real-world projects cannot be fairly ported to all five bundlers due to bundler-specific APIs.
Our solution is a \textbf{two-tier strategy}: controlled synthetic projects provide internal comparisons, and one real-world fixture provides a scoped replication.

Each generated component falls into one of eight template categories---data display (25\%), form control (15\%), layout (15\%), navigation (10\%), feedback (10\%), data fetching (10\%), chart/visualization (10\%), and utility/context providers (5\%)---weighted to approximate the distribution in production codebases.

Critically, each component template is \emph{calibrated}---designed so that specific features exercise specific metrics.

The dependency graph is structured to resemble real projects: each component imports 1--3 siblings within its feature folder; 10\% of components have a cross-folder import; and $\sim$2\% are designated as ``hub'' components imported by 20--30 parents.
Circular dependencies are detected and broken by the generator.

For a scoped replication, we select Bulletproof React~\cite{bulletproofreact2024}, an open-source production-architecture reference application with 102 TSX component files, React 18, TypeScript 5, Tailwind CSS, React Query, Zustand, and React Router.
We adapt it for all five bundlers by creating tool-specific configurations that follow each bundler's official documentation, with no tool-specific optimizations beyond defaults.
All configurations are included in the replication package.

\subsection{Measurement Harness}\label{sec:harness}

All experiments were conducted on a single machine to eliminate hardware variability: Apple M2~Pro (12-core, 32\,GB RAM) running macOS~26.5.1 (build 25F80), Node.js~v22.16.0, and npm~10.9.2.
Background processes were minimized during all measurement runs.

\textbf{M2 (production build time)} is measured using hyperfine~\cite{hyperfine2024}, a command-line benchmarking tool that reports per-run wall-clock times.
Before each run, a cache-clearing script removes \texttt{node\_modules/.cache}, \texttt{dist/}, \texttt{.rspack/}, \texttt{.vite/}, and OS filesystem caches where applicable.
We configure hyperfine with zero explicit warm-up runs (\texttt{--warmup 0}) and 10 measured runs (\texttt{--runs 10}).

\textbf{M1 (dev cold start)} is measured by starting the development server process, monitoring \texttt{stdout} for the tool-specific ``ready'' pattern (e.g., \texttt{"Local:"} for Vite, \texttt{"compiled"} for Webpack/Rspack), and recording the elapsed wall-clock time.
This is repeated for 20 independent runs with cache clearing between each.
A 60-second timeout classifies non-responding servers as failures.
All retained M1 results are hash-pinned supplemental data collected in an earlier campaign epoch; unlike M2--M11, they do not have a validated-batch manifest.

\textbf{M3 (incremental rebuild)} uses each tool's \texttt{build --watch} mode.
A dedicated script starts a fresh watch process, waits for the initial build's success marker, modifies an active source file, and measures until the subsequent validated rebuild-completion marker.
Each configuration uses five independent watch sessions with four measured updates per session; inference uses the five session medians rather than treating dependent updates as independent.

\textbf{M4 (HMR latency)} is measured via Puppeteer~\cite{puppeteer2024} controlling a headless Chromium browser.
The script launches the development server, navigates Puppeteer to the local URL, and injects a self-accepted probe module whose exact value is observed in the DOM.
After one untimed synchronization update, HMR latency is measured from the file write to the exact browser-observed marker; any full-page reload invalidates the run.
As with M3, each configuration uses five independent sessions with four updates and session-median inference.

\textbf{M5, M6, and M8 (output properties)} are computed across five clean production builds.
M5 sums generated JavaScript, CSS, and HTML bytes (excluding external maps and copied public files); M6 gzips each generated JavaScript file at level~9 and sums the results; M8 counts JavaScript chunks.
M5/M6/M8 report the five-build median and retain per-build hashes; Rollup's synthetic output varies byte-for-byte, so its predeclared median aggregation is retained with that nondeterminism recorded.
M9 injects a unique source sentinel and checks whether its generated position maps to the exact original source line and column.
M7 uses empty, selected-export, and full-library \texttt{lodash-es} fixtures and reports the percentage of full-library bytes eliminated; fixture builds are independently repeated.

\textbf{M10 (memory)} is derived from the process peak resident set size and normalized to MiB; \textbf{M11} sums user and system CPU seconds from \texttt{/usr/bin/time -l} as a CPU-time proxy for energy demand under controlled load.
Ten independent runs are performed with cache clearing between each.

\textbf{Warm-up and sensitivity.} Production/resource runs have no discarded warm-up observation; medians and IQRs retain all runs. M4 uses one untimed synchronization update to align browser and server compilation generations. A sensitivity analysis removes the first production/resource observation and the first update from every M3/M4 session; none of 136 within-group tool ranks changes.

\subsection{Statistical Analysis}\label{sec:stats}

Our statistical pipeline follows the recommendations of Georges et al.~\cite{georges2007statistically} for non-parametric analysis of performance data.

\textbf{Step 1: Units and descriptive summaries.}
M1/M2/M10/M11 runs are independent process executions. M3/M4 use one median per independent watch/dev-server session. M5--M9 are single accepted aggregates and are excluded from inferential testing.

\textbf{Step 2: Omnibus test.}
For each inferential metric$\times$size combination, we apply the Kruskal--Wallis $H$ test~\cite{kruskal1952use} with average ranks and tie correction ($\alpha = 0.05$).
For M3/M4, the asymptotic chi-square reference is interpreted cautiously because each tool contributes five session units.

\textbf{Step 3: Pairwise comparisons.}
We conduct Dunn post-hoc comparisons using global ranks and tie-adjusted rank variance, with Bonferroni correction~\cite{bonferroni1936teoria} within each metric$\times$size family.

\textbf{Step 4: Effect sizes.}
For every pair, we compute Cliff's delta~\cite{cliff1993dominance} and a deterministic 5{,}000-replicate percentile bootstrap interval.
Positive delta means the first tool has larger values; intervals are descriptive and not multiplicity-adjusted.
We interpret $|\delta| < 0.147$ as negligible, $< 0.33$ as small, $< 0.474$ as medium, and $\geq 0.474$ as large~\cite{vargha2000critique}.

\textbf{Step 5: Scaling regression.}
For each tool, we fit linear, log-linear, and quadratic models to the five Tier~1 M2 medians.
We report $R^2$, adjusted $R^2$, and leave-one-size-out RMSE, selecting the model with the lowest held-out RMSE.

All analysis code is implemented in TypeScript (executed via \texttt{tsx}) using the \texttt{simple-statistics} library and is included in the replication package.

\section{Discussion}\label{sec:discussion}

\subsection{Key Findings Summary}\label{sec:findings}

Our study yields four principal findings that collectively demonstrate there is no single ``best'' JavaScript bundler---the optimal choice depends on project scale and priorities.

\begin{enumerate}[leftmargin=*,label=\textbf{F\arabic*.}]
  \item \textbf{Scale-dependent build-speed leadership.} esbuild has the lowest M2 median through 2{,}000 modules; Vite has the lowest at 5{,}000, with their xl pair not significant after Bonferroni correction.
  \item \textbf{Development metrics distinguish different operations.} Rspack has the lowest M3 median at every scale, while Vite has the lowest M1 and M4 medians.
  \item \textbf{Scaling form differs by tool.} LOOCV selects linear M2 models for Vite and Rspack and quadratic models for esbuild, Rollup, and Webpack.
  \item \textbf{Scoped real-world replication.} Bulletproof React preserves the synthetic M10 ordering but swaps Vite and Rspack for M2 and M11, bounding rather than proving generalizability.
\end{enumerate}

\subsection{Practical Implications}\label{sec:practical}

Based on our findings, we propose the decision framework in Table~\ref{tab:decision}.

\textbf{Rspack as a Webpack migration path.}
Rspack's Webpack-compatible API can reduce migration effort, although compatibility was not an experimental outcome.
At m-500, its M2 median is 2{,}190\,ms versus Webpack's 10{,}665\,ms (4.9$\times$); at xl-5{,}000 the medians are 14{,}585 and 121{,}520\,ms (8.3$\times$).

\textbf{Vite~8 in the evaluated configuration.}
Vite has the lowest descriptive linear slope (928\,ms per 1{,}000 modules), the lowest xl-5K M2 median, and the smallest synthetic gzip aggregates.
The study does not isolate how much of this behavior is attributable to Rolldown versus other implementation or configuration differences.
The scale-invariant dev cold start ($\sim$868\,ms regardless of project size) further supports Vite's suitability for large projects.

\subsection{Architectural Insights}\label{sec:arch}

\textbf{Observed performance is not a causal architecture test.}
The tool implementations differ in language, algorithms, defaults, and integration layers.
Our controlled workloads compare their resulting behavior but cannot attribute differences to any one factor.

\textbf{Large-scale development performance.}
All five tools complete M3 at xl-5{,}000; Rspack's 351.5\,ms session median is the lowest.
For M4, Vite's 80.5\,ms median is lowest, followed by Rspack at 376.5\,ms and Webpack at 4{,}323.5\,ms.

\subsection{Comparison with Grey Literature}\label{sec:grey}

Our findings qualitatively agree with vendor benchmarks in ranking direction but diverge in magnitude.
The rspack-contrib benchmark~\cite{rspackbench2026} reports Vite's production build as the fastest among the tools we study---consistent with our xl-5K medians but not smaller scales, where esbuild leads.
The divergence arises because vendor benchmarks typically use a single, small project scale, missing the crossover phenomenon that is our central finding.

Both vendor benchmarks and our study rank Webpack and Rollup as the slowest tools.
Our xl-5K M2 medians show a 21.9$\times$ Webpack--Vite ratio.
Differences from vendor benchmarks may reflect workload and configuration choices; the present design cannot isolate a single cause.

\section{Threats to Validity}\label{sec:threats}

We discuss threats following the four-category framework of Wohlin et al.~\cite{wohlin2012experimentation}.

\subsection{Internal Validity}

\textbf{Single machine.}
All experiments were conducted on a single Apple M2~Pro machine.
While this eliminates hardware variability, it limits generalizability to other architectures (x86, ARM server, CI runners).
We mitigate this by reporting relative rankings (which are less hardware-sensitive than absolute times) and note multi-platform benchmarking as future work.

\textbf{First-observation sensitivity.}
The first observation in a session can differ because of caching, JIT compilation, or disk I/O.
We report medians and IQRs, and a prespecified sensitivity analysis excluding first observations changes none of 136 within-group tool ranks.

\textbf{Measurement precision.}
Wall-clock timing via hyperfine (M2) and Node.js \texttt{Date.now()} (M1, M3, M4) has millisecond precision.
For measurements in the range of hundreds of milliseconds to minutes, this precision is sufficient.
Measurement variability is represented by IQRs; bootstrap confidence intervals accompany pairwise Cliff's delta estimates.

\subsection{External Validity}

\textbf{Synthetic projects.}
Despite our calibration effort (8 component templates, 50--150 LOC, realistic patterns), synthetic projects may not capture all characteristics of production codebases.
Tier~2 (Bulletproof React) provides one scoped comparison: it preserves the M10 ordering but swaps Vite and Rspack for M2 and M11.

\textbf{Single real-world project.}
Tier~2 uses only one OSS project (Bulletproof React, 102 files).
Because a single project cannot establish population-level external validity, Tier~2 bounds rather than proves generalizability.
Bulletproof React is a React + TypeScript reference architecture; projects with substantially different dependency profiles (e.g., heavy native modules, monorepos with workspace resolution) may produce different rankings.
A broader validation with multiple projects of varying size, framework (Vue, Angular, Svelte), and complexity is needed and noted as future work.

\textbf{React + TypeScript only.}
All projects use React and TypeScript, the most popular frontend framework and language~\cite{stateofjs2025}.
Results may differ for other frameworks due to different plugin pipelines and transform requirements.

\textbf{Tool versions.}
All tool versions were pinned on experiment Day~1.
Bundler performance improves across releases; our results reflect the state as of September 2026.

\textbf{Phase-batched collection.}
Metrics were collected in separate validated phase batches on the same recorded host with rotated tool orders.
Differences in collection time and background system load may affect cross-metric comparisons even though provenance and host fingerprints are retained.

\subsection{Construct Validity}

\textbf{Metric coverage.}
Our 11 metrics cover build speed, output quality, and resource consumption, but do not measure developer experience factors such as error message quality, configuration complexity, plugin ecosystem breadth, or IDE integration.
These are qualitatively important but require different research methods (e.g., surveys, usability studies).

\textbf{M1 provenance and coverage.}
M1 covers Vite, Rspack, and Webpack but not esbuild or Rollup.
Its 180 observations are hash-pinned supplemental results from an earlier campaign epoch and lack the validated-batch manifest used for M2--M11, so M1 conclusions receive a stronger provenance limitation.

\textbf{Session-based development metrics.}
M3 and M4 use five independent sessions per tool and condition, each summarized by its median measured update.
This avoids pseudo-replication of updates from one long-lived process, but $n=5$ makes the asymptotic Kruskal--Wallis and Dunn approximations coarse; exact adjusted values and effect intervals are retained in the package.

\textbf{HMR measurement.}
M4 measures from a file mutation to an exact browser DOM marker set by the updated module and rejects reloads.
This operationalizes visible propagation for the fixture but does not represent every framework HMR path.

\textbf{Tree-shaking metric.}
M7 is the byte-elimination percentage from a controlled used-versus-unused fixture.
It is more comparable than textual reference counting, but remains a fixture-specific proxy.
M5--M9 have one aggregate analysis unit per tool and condition and are therefore reported descriptively without inferential tests.

\subsection{Conclusion Validity}

\textbf{Non-parametric statistics.}
We use tie-corrected Kruskal--Wallis omnibus tests followed by Dunn pairwise comparisons and Cliff's delta, avoiding distributional normality assumptions.
For M3/M4, inference is over independent session medians, not within-session updates.

\textbf{Bonferroni correction.}
We apply the Bonferroni correction within each metric$\times$size family (i.e., the $\binom{k}{2}$ pairs arising from one Kruskal--Wallis test share a single family-wise $\alpha$).
This is conservative and may produce false negatives for borderline comparisons.
Of 251 Dunn pairs, 126 are significant after correction.
Bonferroni control is conservative, so non-significance is not evidence of equivalence.

\textbf{Effect-size confidence intervals.}
We report Cliff's delta with bootstrap confidence intervals in the replication package.
Intervals for small session samples can be wide and should be interpreted with adjusted $p$-values and descriptive differences.

\textbf{Sample sizes.}
The package contains 1{,}945 raw observations, yielding 1{,}390 analysis units and 1{,}265 inferential-test units.
All 30 omnibus tests are significant; 250 of 251 Cliff's delta estimates are large.
These observed outcomes do not eliminate power limitations, especially for five-session M3/M4 groups.

\section{Conclusion and Future Work}\label{sec:conclusion}

We presented a comprehensive empirical comparison of five production-ready JavaScript bundlers---Vite~8, Rspack~2, esbuild~0.28, Webpack~5, and Rollup~4---across 11 directly measured metrics and one derived scaling analysis at five project scales (50--5{,}000 modules).
Our two-tier benchmarking strategy combines calibrated synthetic projects (Tier~1) with one real-world open-source fixture (Tier~2).
The validated corpus contains 1{,}945 raw observations, 1{,}390 analysis units, and 1{,}265 inferential-test units.

The central finding is that no tool leads every operation: esbuild has the lowest production-build median through 2{,}000 modules, Vite at 5{,}000, Rspack for incremental rebuilds, and Vite for HMR.
LOOCV selects linear M2 scaling for Vite and Rspack and quadratic scaling for the other three tools.
Tier~2 reproduces some rankings and changes others, so its evidence is deliberately scoped.
For practitioners, we provide an actionable decision matrix (Table~\ref{tab:decision}) based on project scale and priorities.

\medskip\noindent\textbf{Future work.}
\begin{enumerate}[leftmargin=*]
  \item \textbf{Multi-platform benchmarking} on Linux CI runners, x86 servers, and ARM cloud instances to test hardware generalizability.
  \item \textbf{Turbopack} once a stable standalone production build is available outside Next.js.
  \item \textbf{Longitudinal study} tracking performance changes across bundler versions over 12--18 months.
  \item \textbf{Framework diversity}: replicating the study with Vue, Angular, and Svelte projects.
  \item \textbf{Additional Tier~2 projects} of varying size and complexity to strengthen external validity.
  \item \textbf{Developer experience metrics}: error message quality, configuration complexity, and plugin ecosystem analysis via surveys and usability studies.
\end{enumerate}
